# ポケコンで Switch を操作する

Poke-Controller は画面を持たない本体と、ブラウザーの操作画面、MCP の道具でできている。Switch 1 台ごとに別のプロセスで動き、操作画面のタブ・MCP のセッションが 1 台ずつに対応する。

## 安全のための決まり

- 実機につながっていると、ボタンもスクリプトも本当にゲームを操作する。**利用者が頼んだ操作だけ**を行う。
- A・HOME など、ソフトの起動・終了や決定につながるボタンは特に注意する。迷ったら押す前に聞く。
- 押した結果は、必ず `get_capture` の映像で確かめてから次に進む。
- 細かいタイミングが要る操作は、1 つずつ押さずに `run_sequence` か既存のスクリプトで行う。
- `web_url` やトークンは会話に書かない。`runtime\controller-*.json` も共有しない。
- 画面のテストのために、キー入力を操作画面の窓やページに送らない（「キーボードで操作」がオンだと Switch に届く）。見た目の確認は `app.py --demo` のデモで行う。

## 台（セッション）の選び方

1. `list_sessions` で一覧を取る（本体が止まっていれば起動する）。`label` が台の名前（タブ名）、`switch_state` が状態（ready / starting / restarting / crashed）。
2. 利用者が「2号機で」などと言ったら `label` で選ぶ。指定がなければ、1 台ならその台、複数なら聞く。
3. `ready` でない台は操作できない。`restarting` は自動で戻るのを待つ。`crashed` は原因（記録の `detail`）を伝え、頼まれたら `restart_switch`。

## 利用者に伝える

- 作業を始めたら `set_status` で、目標（task）と「今ゲームの中でしていること」（doing）、必要なら進み具合（progress）を、ゲームの言葉で書く。例: task「色違いのヒトカゲを厳選」、doing「タマゴが孵るまで自転車で往復中」、progress「12/50」。変わったら更新し、終わったら空にする。
- 区切りごとに `add_note` で、何をしたか・どうなったか・今どこまでか・次に何をするかを書く。例「ヒトカゲのタマゴを50個孵化。色違いは出ず。ボックス3まで埋まったので、次はボックス4から。」
- 利用者のメモは `get_assist` で読み、作業の前提にする。
- スクリプトがダイアログを出したら `get_dialogs` で読み、利用者の意図に沿って `answer_dialog` で答える（わからなければ聞く）。
- スクリプトが自分で窓を出す（開始時の設定ウィンドウ、状況表示、cv2.imshow など）ときは、`list_windows` で探し、`get_window` で見て、`operate_window` で選択・入力・ボタンを押す。開始時に設定ウィンドウを出すスクリプトは、その窓を閉じる（「開始」などを押す）まで始まらない。

## 長時間の実行を見張る（頼まれたときだけ）

- `wait_for_incident` で待ち（返った `last_id` を次の `after` に渡す）、知らせが来たら `get_capture` で画面を確かめる。
- エラーの画面なら閉じる、ソフトが止まっていれば HOME からソフトを終了して起動し直す、など、ゲームを元の状態に戻してから `start_script` で再開する。戻せないときは止めたまま、何が起きたかを `add_note` に残す。通知は本体が送る。
- 映像が止まっても、本当に止まっているとは限らない（長い演出など）。画面を見て判断する。
- 記録の `clip` は直前 30 秒の録画。`get_recording_overview` で何が起きたかを見てから直す。
- `kind` が `crash` の記録は、その台のプロセスが落ちたもの。本体が自動で起動し直す。

## そのほか

- 開始・停止の成功は「受け付けた」という意味。結果は `get_logs` と `get_capture` で確かめる。
- スクリプト実行中と COM 未接続のときは、手動のボタン入力は受け付けられない。
- 機器（カメラ・COM ポート）の選択は `list_devices` / `configure_devices`。設定（通知・見張り・コントローラーなど）は全台共通。
- スクリプトを新しく作るときは `script` スキル、操作画面を開くときは `open` スキル。
